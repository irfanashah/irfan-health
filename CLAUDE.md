## Decisions made

- **Dark mode default**, light toggle available, no system-preference following. Persists in localStorage per page load.
- **No `tailwind.config.ts`.** Tailwind v4 reads config from CSS (`app/globals.css`). Spec assumed v3; translated to v4 equivalents.
- **shadcn base preset = `base-nova` (neutral)**, not Zinc as the original spec asked. Visually near-identical; not worth hand-editing 30+ oklch variables.
- **Single-user auth.** Supabase email signup disabled. Only Irfan's account exists.
- **Vercel deploys from `main`.** Every push triggers production. No preview-branch strategy.
- **Vercel Pro plan** (upgraded mid-Slice-1). Required because Hobby caps cron at 2 invocations/day and our `0 */6 * * *` schedule runs 4×/day. Pro also gives function `maxDuration` up to 800 s — the refill/backfill/diagnose routes set `export const maxDuration = 800` to use the full ceiling.
- **OAuth tokens live in Supabase `oauth_tokens` table**, NOT Vercel env vars. Deliberate deviation from data-model spec §6 — documented at top of `slice-1-whoop-adapter-spec.md`. Service-role client reads/writes the table; tokens never reach the browser.
- **Whoop history starts at 2025-02-06** (first day Irfan wore Whoop). The cron-run `BACKFILL_START_DATE` in `adapters/whoop/index.ts` is set to `2026-04-15` (just before the 2026-04-28 STEMI) for routine catch-up runs. Full historical loads use `/api/refill/whoop` (ID-diff approach), which is faster and more reliable than the chunked sweep.
- **`adapters/whoop/api.ts` targets Whoop Developer API v2.** v1 endpoints return 404s — Whoop deprecated them.
- **Dashboard is intentionally minimal post-Slice-1.** Only `DiagnoseButton` is rendered (now showing both Whoop and Withings panels in one click). The Slice-1-era `RunNow`, `Refill`, and `Backfill` buttons + components remain in `components/` and their routes are live; just unrendered. Routine sync runs on cron; reconciliation is a manual job that re-imports the relevant button when needed.
- **Slice 2 default refill `targetStart` is `2025-01-01`**, same as Whoop. The Withings adapter `BACKFILL_START_DATE` matches. POSTing `/api/refill/withings` with `{ fromDate: '…' }` overrides per-call.
- **Withings `attrib` filter:** the adapter and refill both accept `0` (device-recorded), `1` (manual entry via app), `2` (manual override) only. They skip `4` (user objective), `5` (flagged wrong), `7` (creation stub), and any unrecognised value. The `ACCEPTED_ATTRIB` set lives in `adapters/withings/index.ts` and is mirrored inline (with a comment) in `app/api/diagnose/withings/route.ts` — change all three together if loosening.
- **Withings `buildBpRow` is the single source of truth for "what's a valid BP row"**, exported from `adapters/withings/index.ts` and imported by both the cron adapter (via the `withingsAdapter.fetchAndIngest` loop) and `/api/refill/withings`. Avoids drift (gotcha #25).
- **Slice 3 Note lives as an always-visible compact textarea, not a 5th tab.** The data model treats `note` as a peer `metric_type` value alongside `symptom`/`weight`/`glucose_fingerstick`, but standalone notes are rare enough that a tab slot would over-rank it. Always-visible "Quick note" keeps the path open without elevating it to one of the four core types.
- **Single polymorphic `updateEntry({kind,id,payload})` for Slice 3 edits, not per-type updaters.** Create paths stay per-type (`createWeight`, `createGlucose`, …) because their validation differs; updates centralise around the discriminated union so the `source_slug='manual'` guard lives in one place. Asymmetry between create + update is intentional.
- **Symptom severity is optional (nullable 1–5) in Slice 3.** Logging a symptom mid-event shouldn't force a number on you — the code + timestamp is the load-bearing signal; severity is incremental.
- **`source_slug='manual'` is the hard guard on Slice-3 edit/delete.** Every `updateEntry`/`deleteEntry` query chains `.eq('source_slug', 'manual')` with `{count: 'exact'}` — non-manual ids never match, so the action returns "not found or not editable" without distinguishing missing from forbidden. Application + query-level enforcement; no DB-side trigger.
- **Nightscout auth = static URL + read token, NOT OAuth.** No `oauth_tokens` row, no token refresh. `NIGHTSCOUT_URL` + `NIGHTSCOUT_TOKEN` live as Vercel env vars; the token is passed as `?token=…` on every request. The read-only role (subject `irfan-health`) is sufficient — we only ever GET.
- **Slice 5 `BACKFILL_START_DATE` = `2026-05-01`** (not `2025-01-01` as Whoop/Withings use). Nightscout history starts `2026-05-28` (Clarity backfill), and the G7 was the only CGM Irfan has ever worn — no older data can exist. Stretching the default back to Jan 2025 would mean ~17 empty 30-day refill chunks for zero gain. POST `/api/refill/nightscout` with `{ fromDate: '…' }` overrides per-call.
- **CGM plausibility band = 40–500 mg/dL** (not 10–600). Real CGM output starts at 40 — Dexcom G7's measurement range is 40–400 and Libre's is 40–500. Anything below 40 is a sentinel/special code (0, 1, "LOW" encodings), not a reading. 40–500 stays device-agnostic (covers both Dexcom and Libre) while excluding all sub-40 sentinels that a 10–600 floor would let through and pollute trends. If real readings ever get filtered, the skip count surfaces in `ingestion_log` and Diagnose; widen then.
- **Slice 5 `extras` omit-missing rather than null.** `buildCgmRow` writes `{ direction, device, noise }` excluding any undefined key. A backfilled Clarity row carries no `direction` key at all rather than `direction: null`. Querying `extras->>'direction'` returns null either way; this just keeps the JSON compact for the largest writer (Clarity backfill).
- **Slice 5 Diagnose default window = last 30 days** (not full history like Whoop). CGM volume makes a wide default expensive; the refill route is the right tool for true full reconciliation. Diagnose is the quick health check. `POST { fromDate, toDate }` overrides for the rare full check. Different from Whoop's panel deliberately — they're independent.
- **Slice 5 cron passes a strict 48 h window to the adapter** rather than relying on the adapter's last-success-end resolution. Catches missed runs without ever trying to backfill 3 weeks of history in a single 12-hourly tick. Refill is the only path that walks the full history.
- **`buildCgmRow` is the single source of truth for "what's a valid CGM row"**, exported from `adapters/nightscout/index.ts` and imported by both the adapter (cron + ingest) and `/api/refill/nightscout`. Same pattern as Withings `buildBpRow` — avoids drift (gotcha #25).
- **Slice 7.1 charts are custom SVG, NOT recharts.** The Slice-7 pre-spec notes mentioned recharts; the working prototype superseded that with hand-rolled SVG (`Sparkline`, `TrendChart`, `CGMChart`, `Donut`, `StackedBars`) tuned to the design language. Don't add a chart library — port `prototype-src/06-charts.jsx` whenever a new chart is needed.
- **Aggregation is server-side (`daily_metrics` view), not client-side.** CGM is ~288 rows/day; pulling raw and grouping in JS doesn't scale and obscures the time-window rules. The view does CGM stats + GST bucketing in SQL; the dashboard pulls one row per day for whichever range it needs.
- **Whoop daily-summary attribution = wake day, derived from each cycle's MAIN sleep — NOT `period_end::date` for the recovery-family metrics.** Recovery / strain / HRV / RHR rows carry `period_end = CYCLE end` (the next evening, when Whoop closes the cycle); only **sleep rows** carry `period_end = wake morning`. Bucketing recovery by its own `period_end` mis-dates any cycle whose end crosses GST midnight (live bug fixed 2026-06-25 in `migration_003`'s `whoop_daily` CTE — see gotcha #74). The view now derives `wake_day` from each cycle's `sleep_duration_total` row and JOINs the recovery family to it on the shared `period_start`. In-progress cycles have NULL `period_end` (gotcha #17) → no wake_day → naturally excluded. Don't switch to `period_start::date` either — for a Tue-morning cycle that started Mon evening, period_start::date is Mon and the metrics belong on Tue.
- **Weight carry-forward is for the TREND CHART only, never the KPI.** The `daily_metrics` view returns weight = NULL on no-reading days (pure aggregation). `components/dashboard/utils.ts::carryForwardWeightForTrend` fills nulls only for the line chart. The "Latest weight" KPI reads from `fetchLatestKpis()` (actual most recent reading). Mixing the two would show a carried value as if it were today's reading.
- **Recovery-day counter date = 2026-04-28 (STEMI), not the prototype's April 5.** `prototype-src/02-data-layer.jsx` hard-codes April 5 as a placeholder; `CLAUDE.md` is canonical. `components/dashboard/thresholds.ts::STEMI_DATE` uses 2026-04-28 with explicit GST offset.
- **TIR is count-based, valid because sgv is ~5-min equispaced.** Both the `daily_metrics` view (per-day TIR in `cgm_stats`) and the Glucose panel (24-hour TIR donut) use count% as a proxy for time%. The view comments the assumption explicitly; if a future source ever writes non-uniform CGM cadence, switch both to a time-weighted calculation.
- **Glucose panel's 24h TIR is computed from the SAME 24h window the chart shows**, not from the view's per-day TIR. Otherwise the donut and the curve could appear to disagree at the rollover between days — UX confusion. The view's TIR is for the trend / Connections view (Slice 7.2).
- **Slice 7.2 honesty layer: every `r` is computed AFTER `pairedNonNull`** (drops days where either side is null), `n` is ALWAYS displayed next to `r`, and below `MIN_PAIRED_N = 10` the badge greys + the linear fit on the scatter is suppressed + the insight slot reads "Not enough paired days yet (n = X) — keep logging." Don't expose a "filter nulls = off" affordance; pretending zero is a value silently lies on this kind of data.
- **Insight + cascade prose is associational, never causal.** Audited against the prototype: "Short sleep nudged BP up" → "On shorter-sleep days, morning BP tends to run higher." Acceptable verbs: "ran higher / ran lower / linked with / tends to / averaged". Forbidden: "caused / led to / because of / drove". Same rule applies to any future on-dashboard prose.
- **Cardiac Readiness "today" uses a latest-complete fallback** rather than dashing through the day. If today's row lacks any of the five inputs (very common — today's cycle isn't scored yet until Whoop closes it overnight), the panel shows the most recent fully-scored day with an "As of <day> · today's cycle isn't scored yet" sub-note. Delta then compares the two most recent fully-scored days. Only "—" when no day in the window has all five inputs. Decided 2026-06-19 — friendlier UX than a persistent dash, still honest about what's actually being shown. The TREND chart stays strict (only fully-scored days).
- **Readiness never renormalises over missing inputs.** `computeReadiness` returns null if any of the five sub-scores can't be computed. Renormalising would silently change what "70" means day to day. The trend chart shows gaps; the headline uses the latest-complete fallback.
- **Annotated glucose markers reuse the already-pulled `fetchRecentManual(20)`** — no extra round-trip. Risk: on a heavy-logging day a within-window symptom could fall outside the last-20, in which case markers look incomplete. Trivial at current volumes; switch to a window-scoped uncapped query (`recorded_at ∈ [t0,tN]`) if it ever shows up as a real gap. Don't add a second query speculatively.
- **Slice 7.3 separation: `metric_drift` view emits STATS ONLY.** No gate verdict, no thresholds, no `suppress_alerts` handling. The TS layer (`drift-config.ts` + `drift/evaluate.ts`) owns the abs+z AND-gate, the three sufficiency states, the recency-to-today guard, the ≥M held-data-day persistence count over the 14-day bounded look-back, the tier surfacing, direction/Win logic, and clinical-precedence layering. Matches the 7.1/7.2 SQL-stats / TS-interpretation split — thresholds live in TS, one place.
- **Persistence is data-day based, NOT calendar run-length.** The TS layer scans rows in `[today - 13, today]` and counts gate-trip data-days; M=7 confirms drift. Carry-forward across no-data days is forbidden by construction (the view only emits rows for data-days). A mid-stint data stop resets the in-progress count — only real readings count. Most reviewed point in the spec, easiest to get wrong.
- **Recency-against-today, NOT against the latest row.** A row existing doesn't make it current. The TS layer checks `today − latest.date ≤ RECENCY_GUARD_DAYS = 6`; older latest rows → `no-recent-data` (panel says nothing). Spec v1.3 fix — without this, a CGM stint that ended 10 days ago would render a "live" verdict.
- **Anchor supersede is atomic via the `set_anchor()` PL/pgSQL function**, not app-level. The partial unique index `WHERE active = true` on `anchor_sets` makes the naive "insert new active → flip prior" pattern fail (the new row would conflict before the flip runs). The function does flip-then-insert-then-lines in one tx. Don't try to replicate from app code.
- **Med-change reset applies uniformly to rolling + short + prior**, not just rolling. Partial reset (e.g. "let prior span pre-change data") would compare new-normal against old-normal and manufacture drift — exactly the thing the marker exists to prevent. Affected metrics correctly revert to `establishing` until ~28 days of post-change data accrue. Intended.
- **RHR-down is intentionally NOT a Win** in `DRIFT_CONFIG.rhr.acknowledgeGood = false`. For a beta-blocked post-MI patient a falling resting HR can be over-beta-blockade, not fitness. Provisional pending Dr. Jose. The other 7 metrics acknowledge good drift (HRV↑, weight↓, TIR↑, glucose-var↓, sys↓, dia↓, fasting↓). Caution-buffer demotion also applies — a downtrending value goes neutral as it approaches the low floor, never celebrates up to the cliff.
- **Slice 7.3 `extras` exclusion is half-only at the SQL layer.** The view applies `exclude_from_baseline` but NOT `suppress_alerts` — the TS layer queries `context_periods` separately for the latter so the panel can render "suppressed — <type>" without ever silently faking 'stable'. Underlying stats stay honest regardless of suppression; the label is purely UI.
- **The 1-day "exclude today" quick action writes flags EXPLICITLY**, not via multi-day defaults. `type='anomaly', exclude_from_baseline=true, suppress_alerts=false` written by `excludeTodayAction()`. Multi-day context-period form defaults BOTH flags true. Spec is explicit about this split — don't unify them.
- **Anchor metrics with `n < 5` in the source window are deliberately NOT frozen.** Partial anchors are valid. The `/baselines` preview table labels which metrics will/won't be frozen so you can choose a wider window if you want weight/CGM included. The drift evaluator then falls back to rolling for metrics with no frozen anchor stats.
- **Slice 4 drop surface is Google Drive + service-account pull**, not a webhook or upload UI. Drive Desktop on the Mac gives a local-folder UX without standing up our own auth/storage. The service account sees ONLY the explicitly-shared root folder (least privilege). `GDRIVE_SA_KEY` is the JSON key BASE64-encoded — newline mangling in env-var UIs is the documented hazard; the runbook + the Drive client both expect base64.
- **`csv-parse` (battle-tested) is the file-drop pipeline's standard CSV utility**, not a hand-rolled splitter. v1 only has Oxylink, but Contour and future CSV sources ride the same layer; a quote-aware splitter is the kind of thing that works until an escaped quote or empty quoted field silently mis-columns a reading on a cardiac-care platform. 80 KB is nothing in a serverless function.
- **Wake-day attribution = `period_end` GST date, as-is.** No `SLEEP_END_HOUR_CUTOFF`. Spec is unambiguous; an evening-only nap export would attribute to the day you laid down, not the morning. Accepted v1 limitation ("one session per file"); flagged but not fixed.
- **Drift guard on Oxylink parsing: `parse_errors > rows_valid` → fail the file**, not summarise off the survivors. Catches the silent timestamp-format change where `validate()` (header) still passes but most rows return nulls — a real risk for a CSV format you don't control. Cheap, no arbitrary percentage threshold, loud when triggered. Applies to any future parser that follows the same pattern.
- **0 valid rows after filtering → fail the file**, not `success records_written=0`. A sensor-off-all-night export must not masquerade as a clean empty ingest. Reasoned in the parser's return value; moves to `failed/<source>/` with a logged reason on `/diagnostics`.
- **File-drop subfolder resolution: by name on each cron run, in-process cached.** No `GDRIVE_*_FOLDER_ID` env-var pins per subfolder — robust to rename, one less thing to drift. `processed/<source>/` and `failed/<source>/` are auto-created on first run; only `inbox/<source>/` MUST exist (its absence = source not configured, cron skips it).
- **Each file-drop ingestion_log row is written DIRECTLY**, not via `createIngestionLog` (which mandates a window). The fetch window is the parsed session's `period_start`/`period_end` (so `daily_metrics`-style date-window queries can find these); `raw_payload` carries `{filename, drive_file_id, parser, skip_breakdown: {sentinel, out_of_range, parse_errors}, rows_seen, rows_valid, ...summary.meta}`. Matches gotcha #26 (manual/episodic writes bypass the window-only constructor).
- **Baselines & drift lives in its own third top-level tab** (Dashboard · Correlations · Baselines & drift), not as a panel on the Dashboard tab. Crowding it with cardiac/glucose/sleep panels dulled the calmer hierarchy of the redesign; on its own canvas the overall-read band + 5 tiers do the "am I okay?" job in one glance. Tab switch is in-place — the baselines payload is fetched server-side once and reused across tabs.
- **The redesign keeps the drift engine untouched** — no change to `migration_004` `metric_drift` view, `drift-config.ts` thresholds, or `evaluate.ts` gate/persistence/recency. The only data-layer change was widening `fetchMetricDrift` to 30 days. Same SQL-stats / TS-interpretation split as 7.3; the redesign is a tab move + view rebuild + a pure TS mapping layer over the existing stats.
- **`components/dashboard/drift/present.ts` is the single mapping point from engine → design.** Every per-signal field the renderer reads (lo/hi band, dirWord/magWord, pattern counts, confidence wording, source label, lead sentence, state remap) lives in `buildDriftPanelData()`. If anything later turns out to deserve canonical status (e.g. the band) it moves into the view — but until then, presentation-derived stays in one file.
- **"Your normal" band = `rolling_median ± 2 · rolling_mad`** (Decision 1: k=2). Display-only — the gate still uses the real thresholds in `drift-config.ts`. Tuning k changes only what users see in the BandSpark + lo/hi readouts; the alert behaviour is unaffected.
- **`watch` tier renders in "Worth a look" with an "early — not yet confirmed" tag** (Decision 2), and is counted as *emerging* (not confirmed) in the overall-read copy. Irfan chose earlier warning over the calmer fold-into-Steady default; the tag preserves honesty about confirmation. `caution` (low-floor approach, not breached) likewise renders in "Worth a look" but with a distinct lead ("edging toward your low line") so a floor-approach doesn't blur with a drift-from-normal (Decision 3).
- **`magWord` from `|short_vs_prior_z|`**, NOT from the verdict's `shiftZ`: <1.2 "a little" · 1.2–2.5 "noticeably" · >2.5 "well" (Decision 4). Spec-pinned to short-vs-prior even when an anchor is active — the magnitude word describes the recent move, not the gate-driving baseline.
- **Source-label map keys SpO2 to "Oxylink"** (the Claude Design source only knew Whoop/Withings/CGM). `SOURCE_LABEL` in `present.ts` is the single place to extend when a new device lands — every signal card pulls from there. Spo2_avg/spo2_min flow through automatically since `DRIFT_METRICS` already includes both.
- **Suppressed metrics drop to `steady` with a `paused` flag**, never into `safety`/`drift`/`improvement`. Same honesty rule as the previous panel (#44) — alert state is purely UI labelling; the underlying stats stay computed honestly. A breach still wins precedence over a Win at the per-card level (clinical-low precedence guardrail) regardless of suppression.
- **Oxylink desaturation = screening-grade, NEVER diagnostic.** ODI runs on a consumer ring at ~4 s sampling, not a titrated PSG; the algorithm is a deliberately-simple approximation of AASM. All clinical constants (`ODI_*` in `parser.ts`, `st.odi(v)` band, `LOW_FLOORS.spo2_*`) are flagged provisional pending Dr. Jose, and the panel + drift card carry "screening, not a diagnosis" + the `LOW_FLOOR_PROVISIONAL_NOTE`. Don't claim diagnostic accuracy anywhere in the UI; if a value looks worrying, the response is "bring this to Dr. Jose", not "diagnose".
- **ODI + summary numbers computed on the FULL ~4 s in-memory series at ingest; the stored display curve is downsampled separately.** Two distinct passes. The clinical metrics never see the downsampled array — they walk the sorted `rows[]` directly so event detection (≥3% drops, ≥10 s duration, ≥10 s separation, 120 s trailing baseline) preserves accuracy at sensor cadence. Only the *trace we draw* is downsampled to 20 s buckets (~700–1,200 pts/night) to keep storage at ~40 MB/yr. If you ever rewrite the parser, never downsample before the desaturation pass — the algorithm needs the full resolution to find sub-15-second events.
- **Overnight SpO2 curve = ONE JSONB-array row per night, NOT per-reading rows.** `metric_type='spo2_overnight_curve'`, `data_shape='daily_summary'`, `numeric_value=null`, curve packed into `extras` as `{ interval_s: 20, start_ts, spo2: [number|null, …] }`. Reasoned: we only ever read the curve whole-night-to-draw — never query individual points in SQL. ~5,900 per-reading `time_series` rows/night was the obvious alternative and was explicitly rejected: it would collide with the 1000-row cap (gotcha #10) on a single night's pull, force a new index, and balloon the table by ~2.1M rows/year for no analytic gain. Per-night JSONB is ~50–150 KB, ~40 MB/year, no new index, one fetch to render. If point-level cross-night analytics is ever wanted, that's a future dedicated analytics store — not this app's primary table.
- **Both new desaturation metrics are `concerning='up'`, `acknowledgeGood=true`** — the inverse of the SpO2 avg/min calls. ODI and time-below-90 are floored at zero with a clean "good direction" (lower = healthier); a sustained drop is a real win worth surfacing. SpO2 avg/min sit at the high end of a bounded range (≤100) where there's no analogous good drift, which is why they stay `acknowledgeGood=false`. Don't unify the four metrics' direction config — they're physiologically different.
- **`validRecordingHours` sums clipped inter-sample gaps**, not the raw `(lastTs - firstTs)` duration. Each gap caps at `ODI_MAX_GAP_S=60` s, so sensor-off stretches (gap larger than that) don't count toward the denominator. Without this clip, an 8-hour session with a 2-hour sensor-off block would inflate `validRecordingHours` and depress the ODI rate as if those 2 hours had been event-free recording. Same logic applies to `time_below_*` aggregations.
- **ODI is suppressed (`numeric_value=null`) below `ODI_MIN_HOURS=2`.** A wild rate off a 20-minute nap export would be louder than the data deserves. The view's `MAX(...) FILTER (...)` returns null for that night, the dashboard renders "—" in the readout, and `metric_drift` excludes the null (it's a `WHERE … IS NOT NULL` projection). Time-below-90 doesn't get this guard — it's bounded 0–100% by construction so a short session just looks small.

## Gotchas

### Build / project setup
1. **Hardcoded Tailwind colours kill dark mode silently.** `bg-gray-50` on a full-viewport wrapper covers the dark `body` even though `<html class="dark">` is being set correctly. Always use semantic tokens (`bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `border-border`, `border-input`, `ring-ring`, `bg-primary`, `text-primary-foreground`, `text-destructive`, `text-accent-teal/purple/amber`) on any new page.
2. **Next.js 16 deprecated `middleware.ts` → `proxy.ts`.** Warning only; still works. Rename in a future small slice.
3. **`create-next-app` refuses to scaffold into a directory containing arbitrary files.** Slice 0 worked around this by scaffolding in `/tmp` and copying in.
4. **`.gitignore` from `create-next-app` blocks `.env.local.example`** via the broad `.env*` rule. Added `!.env.local.example` exception.
5. **next-themes requires `suppressHydrationWarning` on `<html>`.**
6. **The `@AGENTS.md` import at the top of this file is load-bearing** — it pulls in the "this is Next.js 16, not your training data" notice. Keep it.

### Supabase
7. **`createClient` (server) is async** (`cookies()` is async in Next 16) — must be `await`ed. **`createServiceClient` (service) is sync.** Slice 1 spec mixed these up; fixed inline.
8. **Postgres `numeric` round-trips as either number or string** through PostgREST. The dedup pre-check in `upsertObservation` coerces both sides via `Number()` before `===` — without that, the "skipped" counter never increments even though dedup at DB level still works.
9. **Middleware must not redirect `/api/*` routes.** Spec's Slice 0 middleware redirected every non-`/login` route to login if unauthenticated; that swallowed Whoop's OAuth callback (the `code` param was lost on the redirect to `/login`). API routes self-enforce auth — session for `/api/ingest/whoop`, `CRON_SECRET` for `/api/cron/whoop`, public for OAuth callbacks.
10. **Supabase JS `.select()` silently caps at 1000 rows by default.** Bit us twice — first in the diagnose route (per-metric counts were truncated), then in the refill route's "fetch all existing IDs" step. Fix: either use `.select('*', { count: 'exact', head: true })` for count-only, or paginate with `.range(offset, offset + 999)` for actual rows.
11. **Batch upserts are all-or-nothing per statement.** One row with a check-constraint violation (e.g. null `period_end` from an in-progress Whoop cycle) fails the entire 200-row batch. Filter invalid rows before the batch call, don't rely on the DB to skip them.
12. **Frontend cursor state must be persisted in `localStorage`** for multi-click backfill UIs — React `useState` resets on page refresh, which silently restarts the cursor from "now" and re-walks the dense recent window. Cost us hours debugging the sweep before figuring this out.

### Source APIs — Whoop
13. **Whoop's developer API is v2 only** at `https://api.prod.whoop.com/developer/v2`. The v1 paths in the original spec returned 404.
14. **Sleep is at `/activity/sleep`, not `/sleep`.** Spec was wrong; cycle and recovery are at `/cycle` and `/recovery` (no `/activity/` prefix).
15. **Whoop requires the OAuth `state` parameter** on the authorization request, not just optional. We generate 32 random bytes hex, store in an httpOnly cookie (`sameSite: 'lax'`, 10 min TTL), and verify on callback. Without it Whoop returns `{"error":"invalid_state"}` immediately, before even rendering its approval page.
16. **OAuth handshake must happen on the live Vercel URL**, not localhost — Whoop's app registration only allows HTTPS redirect URIs. Local dev reads tokens from Supabase so this is fine post-handshake.
17. **In-progress cycles and sleeps have `null` start/end.** The current day's cycle (and sometimes the most recent sleep) won't have an `end` until Whoop finalises overnight. Inserting them violates the `chk_obs_time_coverage` constraint on `health_observations`. The refill route filters these out into `buildErrors`; the next cron run picks them up once Whoop scores them.
18. **Recoveries inside a fetch window can link to cycles just before it.** A recovery scored on 2025-01-01 morning links to a cycle that started on 2024-12-31 evening. If you only fetch cycles for `[fromDate, toDate]`, those recoveries silently drop because their `cycle_id` isn't in your `cycleMap`. Fix: widen the cycle fetch backwards by 14 days, but only emit `strain_score` rows for cycles whose `start >= fromDate` so you don't pollute pre-window data.
19. **Whoop rate-limits aggressively.** Stacking diagnose + refill + ingest in quick succession trips 429 on `/cycle`. Wait ~2 minutes and retry, or — better — verify in Supabase with a SQL `COUNT(*) GROUP BY metric_type` instead of re-hitting Whoop.

### Source APIs — Withings
- **Withings uses form-encoded POST for everything** — both the token endpoint (`/v2/oauth2`) and the measure endpoint (`/measure`) accept `application/x-www-form-urlencoded` POST bodies, including an `action` form field (`requesttoken`, `getmeas`). Don't send JSON.
- **Withings responses are wrapped**: `{ status: number, body: {...}, error?: string }`. `status === 0` means success; anything else is an API-level error even on HTTP 200. Always unwrap and check `status` before reading `body`. Surface `error` text on non-zero status.
- **Withings tokens rotate on every refresh.** New `refresh_token` returned in each `requesttoken` response. Persist the rotated pair to `oauth_tokens` immediately (handled in `refreshAccessToken`). Lose the new refresh token and you have to re-handshake from scratch.
- **Withings `getmeas` paginates via `{ more, offset }`.** Stop when `more !== 1`. Defensive: also stop if `more === 1` but `offset` didn't advance — prevents infinite loop on a misbehaving response.
- **Withings unit field is a base-10 exponent**, not a unit string. Real value = `value × 10^unit`. Example: `{ value: 1200, unit: -1 }` → 120 mmHg. Don't forget to `Math.round()` before storing in `smallint` columns.
- **Withings `attrib` codes encode measurement provenance**, not just metadata. `0` = device, `1` = manual app, `2` = manual override are real; `4` = objective (a target, NOT an actual reading), `5` = flagged wrong, `7` = creation stub. Filter against an explicit allow-list, don't reject only the obvious bad codes.
- **Measurement groups can contain non-BP measurements.** A pulse reading without systolic+diastolic isn't a BP reading and must not land in `bp_readings`. Filter on presence of both `type === 9` and `type === 10` before building a row.

### Vercel
20. **Vercel function timeouts:** Hobby caps at 60 s regardless of `maxDuration`. Pro defaults to ~180 s; `maxDuration = 800` is the Pro ceiling. When the function exceeds its budget, Vercel returns a plain-text "An error occurred…" page — the frontend's `JSON.parse` chokes on it with `"Unexpected token 'A'…"`. That error means "function timed out", not "adapter bug".
21. **Vercel cron limits:** Hobby allows 2 invocations/day total. `0 */6 * * *` = 4/day blocks the entire deploy (not just disables the cron). Required Pro upgrade.
22. **GitHub-App webhook can go stale after a Vercel plan upgrade.** Pushes silently stop triggering deploys despite the Git settings page still showing "Connected". Fix: Settings → Git → Disconnect → reconnect. Confirmed in Slice 1.

### Operational
23. **Session-authenticated routes can't be hit by `curl` from the terminal.** `/api/ingest/*` and `/api/refill/*` check `supabaseUser.auth.getUser()` against the Supabase session cookie. Without the cookie, you get `{"error":"Unauthorised"}` and 401 — even when logged into the dashboard in another tab, because the cookie lives in the browser, not the shell. Quickest one-off: while logged in, paste a `fetch('/api/refill/...', {...})` snippet into the browser dev console — runs in your authenticated tab, cookie tags along automatically. Alternatively re-import a button into `app/page.tsx` and click it.

### Loading patterns
24. **Prefer ID-diff refill over chunked sweep for any "full historical load" task.** The chunked sweep approach (walk windows in N-day chunks, dedup per row via SELECT-then-upsert) is slow (~50 ms × N rows per chunk for the dedup SELECT) and error-prone (cursor management, partial timeouts, every chunk creates an `ingestion_log` row). The ID-diff pattern — fetch the full list of IDs from the source, pull existing IDs from the DB (paginated), diff in memory, batch-upsert only the missing ones — completed the entire 17-month Whoop history in ~13 s after we landed on it. Use the sweep only when memory diff is impractical (millions of records) or when the source doesn't expose stable IDs.
25. **When you fix a row-validity filter in the refill route, back-port it to the main adapter too.** The refill route (`/api/refill/whoop`) was hardened with null-`period_start`/`period_end` filters for in-progress cycles/sleeps. The main adapter (`adapters/whoop/index.ts`) — which the cron uses — was missed initially. Every cron run silently landed as `status = 'partial'` for ~5 errors against the in-progress cycle until we noticed and ported the same filter across. The two paths share the same `health_observations` constraints; whatever the refill skips, the adapter must skip. Same rule will apply per-source going forward: `adapters/<source>/index.ts` (incremental cron) and `/api/refill/<source>/route.ts` (full-history reconciliation) must agree on what gets filtered.

### UI / forms (Slice 3)
26. **`adapters/_lib/ingestion-log.ts:createIngestionLog` mandates a fetch window**, but manual writes have no window — schema already allows nulls (`fetch_window_start/end` are nullable, "null for episodic imports" per data-model spec §1). Slice 3's `actions.ts` inserts the `ingestion_log` row inline with `status='success'` + `records_*=1` + `raw_payload`=form values and no window. Don't try to reuse `createIngestionLog` for manual paths; either keep them separate or relax the helper to accept optional windows.
27. **Use `{ count: 'exact' }` on Supabase `.update()` / `.delete()` to detect "guard failed → no rows touched".** Slice 3's `updateEntry`/`deleteEntry` chain `.eq('source_slug', 'manual')` and inspect the returned `count` — zero means either the id doesn't exist or it's not a manual row, and the action returns the same "not found or not editable" message in both cases (deliberately — don't leak whether a non-manual id exists). This is the right pattern for any future row-level write guard.

### Nightscout / CGM (Slice 5)
28. **Cross-slice import: `adapters/nightscout/index.ts` imports `mgdlToMmol` from `@/app/log/_lib/glucose`.** That helper was written for Slice 3's manual-entry path; Slice 5 reuses it directly rather than duplicating the divisor + rounding. The path `adapters/ → app/log/_lib/` is unusual but intentional. Any future glucose-source adapter (Tidepool, labs with fasting-glucose markers) should reuse this same helper rather than copying the conversion. If it ever needs to move, `adapters/_lib/glucose.ts` is the natural home — but don't move it without updating both Slice 3 and Slice 5 imports.
29. **Nightscout `/api/v1/entries.json` returns 10 entries by default.** You MUST pass `count=…` (we use `100000`) on every request, or you'll silently truncate windows. The cron is small enough that the cap doesn't matter, but the refill's 30-day chunks would lose almost everything without it. Same risk applies to any other Nightscout endpoint (treatments, profiles).
30. **`extras` keys for Nightscout are written omit-missing**, not `null`. Backfilled Clarity rows have no `direction`; the row's `extras` simply has no `direction` key, vs. `{direction: null}`. `extras->>'direction'` returns null either way in SQL, so this is purely about JSON compactness for the bulk-import case. If you later need to distinguish "no direction reported" from "explicitly null", revisit this.

### Dashboard (Slice 7.1)
31. **All GST bucketing in `daily_metrics` goes through `AT TIME ZONE 'Asia/Dubai'`** — never mix UTC and local time in the same predicate. The view uses three flavours: `(ts AT TIME ZONE 'Asia/Dubai')::date` for day-buckets, `(ts AT TIME ZONE 'Asia/Dubai')::time BETWEEN TIME '05:00' AND TIME '11:00'` for time-of-day windows (morning BP, fasting glucose), and the same construct as a CASE sort key in `DISTINCT ON` to prefer morning readings. Any future per-source rule that involves "Irfan's local day" must use the same pattern. Asia/Dubai is fixed UTC+4 — no DST surprises.
32. **The prototype's CSS theme was `[data-theme="dark"]`; Slice 7.1's port uses `.dark`/`.light` to match next-themes' `attribute="class"`.** Don't introduce a parallel `data-theme` attribute — the dashboard CSS picks up the same class next-themes already toggles on `<html>`. If you ever wire a second theme mechanism, the dark/light vars will desync on toggle and one of the two will silently win.
33. **Dashboard body styles are scoped to `.app`, not the global body.** The prototype's CSS had `body { background: var(--bg); }` which would override Tailwind's `bg-background` on `/log` and `/login`. The port moves background + font onto `.app` so the rest of the app's semantic tokens still rule. New dashboard-only styles should hang off classes inside `.app`, not the root.
34. **Charts treat `null` accessor results as gaps, not zeros.** `TrendChart` segments the path on null and only draws within contiguous runs of valid values. Don't replace nulls with 0 in the view or the data module — that would draw a fake "weight = 0 kg" line on no-reading days. Empty-array data renders an "empty note" instead. The same rule applies if you add a new series.
35. **`router.refresh()` after a write is the Slice-7 mutation pattern, not optimistic prepend.** Quick-log calls a Slice 3 server action then `router.refresh()` — Next.js re-runs the dashboard's server component, the recent feed + KPIs come back fresh, no client-side stale state to manage. Use the same pattern for any future dashboard write.

### Connections (Slice 7.2)
36. **Pair before you compute.** Every `r` (Correlation Explorer + Activity pacing) goes through `pairedNonNull(xs, ys)` first; raw arrays are never fed into `pearson`. New copy goes through the same filter: descriptive verbs only ("ran higher", "tends to", "linked with"), never causal ("caused", "led to", "because of"). One leaked "caused" undoes the rest.

### Baselines & Drift (Slice 7.3)
40. **The `metric_drift` view's gate is data-day based, NEVER calendar run-length.** TS counts gate-trip days in `[today-13, today]` (= 2 × short window). Carry-forward across no-data days is forbidden — the view only emits rows for data-days, so non-data days never enter the count. A mid-stint data stop naturally resets the in-progress run. Most-reviewed point in the spec, easiest to get wrong; if you ever change `evaluateMetric()`, this is the invariant to protect.
41. **Recency is checked against today, NOT against the latest emitted row.** `latest.date ≤ today - RECENCY_GUARD_DAYS` → `no-recent-data` regardless of what stats the latest row has. Without this, a 10-day-stale CGM stint would render as a live verdict.
42. **`set_anchor()` is a PL/pgSQL function for atomicity** — the partial unique index `WHERE active = true` on `anchor_sets` prevents app-level supersede (the new INSERT would conflict before any UPDATE could run). The function does flip→insert→insert-lines in one tx. Don't try to replicate from app code; call the RPC.
43. **Med-change reset is uniform across rolling+short+prior**, not rolling-only. Partial reset would compare new-normal against old-normal and manufacture drift — exactly the thing the marker exists to prevent. Affected metrics correctly revert to `establishing` until ~28 days of post-change data accrue. Intended; surfaced in the form's footer copy.
44. **`exclude_from_baseline` is applied in the SQL view; `suppress_alerts` is applied in TS.** The view's `filtered` CTE drops excluded days from EVERY downstream window. The TS layer queries `context_periods` separately to render the "suppressed — <type>" label without ever silently faking 'stable'. Underlying stats stay honest regardless of alert suppression.
45. **RHR-down is intentionally neutral, NOT a Win.** `DRIFT_CONFIG.rhr.acknowledgeGood = false` because a falling resting HR on a beta-blocked post-MI patient can be over-beta-blockade not fitness. Provisional pending Dr. Jose. The caution-buffer also demotes any Win (across all metrics that acknowledge good drift) once the value enters `floor + buffer` — no celebrating up to the low-floor cliff.

### Baselines & Drift redesign (Slice 7.3R — Claude Design tab)
56. **The decoded design uses `[data-theme="dark"]`; the app uses `.dark`/`.light` (next-themes).** When porting any future block from the Claude Design HTML, strip `[data-theme="…"]` selectors and re-root on the `.dark`/`.light` class — a second theme mechanism on the same page would desync on toggle (gotcha #32). For the Baselines & Drift block, the rules I ported reference `var(--*)` only and the variables are already defined under `.dark`/`.light` in `app/dashboard.css`, so the port was a straight copy with no theme re-rooting needed. Watch for `[data-theme="light"] .x` overrides if porting other blocks.
57. **`fetchMetricDrift` accepts `daysBack` (default 30) — the engine's `PERSISTENCE_LOOKBACK_DAYS=14` constant is now independent of the fetch window.** Both numbers live for a reason: the engine's persistence check (≥M held data-days) bounds itself to PERSISTENCE_LOOKBACK_DAYS so a metric's "drift" verdict stays a recent-pattern claim; the redesign's tab wants 30 days for the band sparkline + "X of last 14" framing. Don't conflate them — if you ever tighten the engine's window, the fetch can stay at 30; if you widen the fetch further (e.g. 90), nothing in evaluate.ts changes because it filters internally to its own lookback. Caller passes whatever it needs.
58. **Source-label map in `present.ts` is the ONE place to add a new device label.** SignalCard reads `sig.source` verbatim; metrics not in `SOURCE_LABEL` would render `undefined`. If you add a metric to `DRIFT_METRICS` (and the engine accepts it via `drift-config`), also add a `SOURCE_LABEL[metric] = '…'` entry. The Claude Design only knew Whoop/Withings/CGM — Oxylink was the first new label needed; the next (e.g. Contour for fasting fingerstick, labs for fasting) will follow the same one-line add.
59. **State remap precedence in `buildSignal()` matters and is ordered:** `no-recent-data` → `nodata`; `establishing` → `settling`; `clinicalLow === 'breach'` → `safety` (overrides any tier); `clinicalLow === 'caution'` → `drift`+caution (overrides Win/Drift framing because a floor-approach is a different concern); tier-`drift` → `drift`; tier-`watch` → `drift`+early; tier-`win` → `improvement`; else `steady`. Suppression overlays each: if `alertsSuppressed`, anything that would have been `safety`/`drift`/`improvement` drops to `steady` with a `paused` flag — the verdict is still computed honestly, only the UI tier label is suppressed. Don't reorder these branches without thinking about the breach-over-Win / caution-over-Win interactions; that's where honesty leaks would start.
60. **`series` is calendar-day padded, not row-list passed through.** `buildSeries()` builds a `daysBack`-long array; days with no row become `{v: null}` (gotcha #34 — gaps, not zeros). The BandSpark filters nulls at render time but PRESERVES the array indices so `windowDays` ("recent emphasis") slices the right tail correctly. If you switch series to rows-only, the recent-emphasis dots will mark the wrong points and gap-spacing collapses.

### Oxylink desaturation (Overnight Oxygen panel)
61. **Don't downsample BEFORE the desaturation pass.** Two passes, in order: (1) compute ODI / time-below / distribution over the FULL sorted `rows[]` in `computeDesaturation()`, (2) downsample for the *display* curve via `downsampleSpo2Curve()`. Reverse the order and short events (≥10 s but <30 s) disappear from the ODI count because they get averaged out of the bucket. The two functions are deliberately independent — the display array is never used as a clinical input.
62. **Curve bucket nulls = sensor-off, not "no average computed".** `downsampleSpo2Curve()` emits `null` when a 20 s bucket received zero samples (sensor disconnected, charging, off the finger). The renderer must treat null as a gap (`Spo2OvernightChart` splits the line into contiguous runs and renders each as its own path). Don't replace nulls with zeros, with `null`-as-94%, or with linear interpolation — gotcha #34 applies here too, and a fake-zero traversal in a SpO2 trace would look like a catastrophic desaturation that didn't happen.
63. **`validRecordingHours` clips inter-sample gaps at `ODI_MAX_GAP_S` seconds.** A sensor-off stretch of 20 minutes contributes ~`bucketCount × 4 s` of valid recording, not 1,200 s, because every inter-sample gap larger than 60 s is dropped from the sum. Same clip applies to `time_below_*` integrations. Without this clip an 8-hour session with a 2-hour disconnect would have its ODI divided by 8 hours instead of 6, depressing the rate as if the disconnect period had been clean recording.
64. **ODI = null when `validRecordingHours < ODI_MIN_HOURS=2`.** `numeric_value: null` on the row → the `daily_metrics` view's `MAX(... FILTER ...)` returns null → that day silently drops out of `metric_drift` (the long_form CTE has `WHERE … IS NOT NULL`). Dashboard renders "—" with `var(--text-dim)`. A 90-minute nap session ingests cleanly but doesn't pollute the ODI signal. Time-below-90 has no equivalent guard — it's already bounded 0–100% by construction.
65. **One JSONB-array curve row/night, never per-reading rows.** `metric_type='spo2_overnight_curve'` carries `extras = { interval_s, start_ts, spo2: [number|null, …] }`. The `extras.spo2` array is keyed off `start_ts + i × interval_s × 1000ms` — the renderer reconstructs timestamps without sending them. If you ever switch to per-reading rows you'd hit the 1000-row cap (gotcha #10) on a single night's pull AND inflate the table by ~2.1M rows/year — both rejected explicitly in the spec. The point-level data IS available in-memory at ingest if anyone ever needs to recompute; for query analytics it goes to a future dedicated store, not `health_observations`.
66. **`numeric_value=null` rows fail check constraints on some schemas; this one allows it.** The `spo2_overnight_curve` row deliberately has `numeric_value=null` (no scalar makes sense for an array). `health_observations.numeric_value` is nullable per migration_001, and the `chk_obs_time_coverage` constraint only cares about `recorded_at` vs `period_*`. If you ever migrate to a stricter schema, this row will be the first thing it complains about — keep the row, relax the constraint.
67. **Desaturation event markers are positioned by TRUE timestamps + TRUE nadirs, never derived from the downsampled curve.** Events are captured by `detectDesatEvents()` walking the full ~4 s `rows[]` and stored on the `spo2_odi` row's `extras.desaturation_events` as `[{ t: epoch_ms_of_nadir, nadir_spo2, drop_pct, also_4pct }, …]`. The chart positions each marker by linearly interpolating `t` into the rendered curve's `[t0, tN]` x-range and clamps `nadir_spo2` into the visible y-domain. A marker can legitimately appear BELOW the visible curve line at that x position — that's correct, the marker shows where the SpO2 actually went, while the curve shows the 20 s bucket average. If you ever switch the events array to be inferred from the curve, marker positions and depths both go inaccurate; keep the parser as the authoritative source.

### Contour fingerstick (Slice 4 follow-on)
68. **Contour timestamp format is its OWN parser — do not share with Oxylink.** Contour exports `MM/DD/YYYY h:mm AM/PM` (US, no leading-zero hour: `5/04/2026 7:18 AM`). Oxylink exports `hh:mm:ssAMPM Mon DD, YYYY` (`10:38:13PM Jun 21, 2026`, no space before AM/PM). Two completely different shapes; trying to unify them would lose information in both directions. `parseContourTimestamp` lives next to its parser and shares NOTHING with `parseOxylinkTimestamp` except the GST→UTC convention (gotcha #31). Both are GST-local, both return UTC instants — every other character differs.
69. **Contour CSV has a UTF-8 BOM before the header (`\xEF\xBB\xBF`).** `validate()` strips it before the prefix-match; `parse()` uses `csv-parse` with `bom: true`. Without the strip, `validate()` sees `﻿#,Date and Time,…` (BOM as the first character) and rejects the file as not-Contour — silent failure mode. Reference: any future parser whose source generates CSV with a BOM (Excel-exported CSVs typically do) needs the same treatment in both places.
70. **Contour `source_record_id` is timestamp+value keyed: `'contour_' + epoch_ms + '_' + bg_mgdl`.** The timestamp is minute-resolution (Contour Next One doesn't emit seconds), so the rare same-minute back-to-back reading needs the value to disambiguate. Stable across exports: a later overlapping export of the same readings dedupes via `(source_slug, source_record_id)`. If Contour ever starts emitting second-precision timestamps, the value suffix becomes redundant — keep it anyway for the rare-but-possible same-second case and the trivial increase in id length.
71. **Contour writes IDENTICAL row shape to Slice 3 manual fingerstick** (`metric_type='glucose_fingerstick'`, `data_shape='discrete'`, `canonical_unit='mmol/L'`), plus `extras` enrichment (`{ meal_marker, data_source, notes }`). Downstream consumers (`fetchFingersticks`, recent-activity timeline) need no per-source branching — they read `metric_type='glucose_fingerstick'` and get both. Don't introduce a `metric_type='glucose_fingerstick_meter'` variant; one type, two sources.
72. **CGMChart fingerstick markers are VALUE-ANCHORED, not curve-snapped.** `kind === 'fingerstick'` plots at `yOf(value)` — its own meter reading — NOT at `yOf(data[di].value)` (the CGM curve value at that timestamp). This is load-bearing for the meter-vs-sensor comparison: a marker visibly above or below the curve line shows real disagreement at that moment. Symptom/note markers (the Slice 7.2 path) DO snap to the curve and that's correct for their purpose (they're time-anchored events, not numeric readings). One chart, two anchoring modes — branched on `kind`. Don't unify the rendering paths.
73. **`fetchFingersticks()` is source-agnostic by design.** Filters only on `metric_type='glucose_fingerstick'` + a recent-hours window — returns Contour + manual rows together. The `source` field on the returned point distinguishes them in the marker tooltip ("Fingerstick — Fasting · Contour" vs "Fingerstick — Manual log"). If a third fingerstick source ever lands (e.g. Apple Health import), it flows through automatically — no reader change.

### Dashboard 7.1 fixes (data correctness + UX + render)
74. **Whoop wake-day attribution: `period_end` IS NOT the wake day for the recovery family.** This is the bug behind the scattered RHR/HRV/Recovery chart gaps that shipped in 7.1 and lived until 2026-06-25. Whoop's `recovery_score` / `hrv_rmssd` / `heart_rate_resting` / `strain_score` rows have `period_end = the CYCLE end` (next evening, when Whoop closes the cycle), NOT the wake morning. Sleep rows (`sleep_duration_total` etc.) DO have `period_end = wake morning` — which is why mis-attribution affected the recovery family but not sleep. Any view that buckets recovery by `(period_end AT TIME ZONE …)::date` will silently mis-date cycles whose end crosses local midnight, collide them with the next day's row, and drop the correct day to NULL after `MAX(...) GROUP BY`. The view's `whoop_wake` CTE derives `wake_day` from each cycle's `sleep_duration_total` row and the recovery family JOINs on the shared `period_start` (every cycle's recovery + sleep share `period_start` — confirmed against live data: Jun 5 recovery and Jun 5 sleep both `period_start = 2026-06-04 19:14:40.64+00`). If you ever add a new Whoop daily-summary metric, route it through `whoop_wake` the same way. The `metric_drift` view reads `rhr`/`hrv` from `daily_metrics`, so this bug also corrupted the Baselines & drift baselines — both auto-correct once the view is fixed (no re-ingestion). Documented separately in the Decisions section above; this gotcha exists so it's never reintroduced.
75. **Glucose panel fingerstick fallback is the third branch, not a swap-in.** The panel has three render branches now: CGM-live (existing CGM "now" + TIR donut + CGM trace with fingerstick overlay diamonds), CGM-stale-but-fingersticks-exist (latest fingerstick as "now" + recent-readings list + "Time in range — Needs CGM data" placeholder), CGM-stale-AND-no-fingerstick (existing empty state). The branch test is `latest.cgm !== null`. Don't fold the fingerstick fallback into the CGM branch — TIR is meaningless without continuous data, and showing 0/0/0 lies about it. `fetchFingersticks(14)` returns enough rows to feed BOTH the 24h overlay markers AND the fallback list with one query — the panel slices internally.
76. **`Sparkline` SVG MUST be `overflow: hidden` + ≤2-point sparse-data short-circuit.** The original ported `Sparkline` had `overflow: 'visible'` AND drew a bezier `smoothPath` for any `data.length >= 2`. With 2 sparse points (e.g. BP measured twice in 2 weeks) the bezier control-point math overshot the viewport and rendered a steep diagonal that bled out of the KPI tile. Fixed by switching the SVG to `overflow: 'hidden'`, plotting the ≥3-point path inside a `[PAD_Y, height - PAD_Y]` band so overshoot stays inside, and short-circuiting `n <= 2` to a short flat centered segment + dot (no bezier). Belt-and-braces `overflow: hidden` on the `.kpi-spark` wrapper too. Same fix protects any future sparse KPI sparkline (HRV early on, weight before regular weighing, etc.).

### Whoop SpO2 / skin_temp
77. **One `metric_type` per CONCEPT — not per source — across all writers.** Whoop and Oxylink both wrote `spo2_overnight_avg` for completely different things (Whoop: a single recovery SpO2 datapoint; Oxylink: an actual overnight average from ~5,900 4 s samples). The collision was latent — the `daily_metrics` SpO2 CTE filtered `source_slug='oxylink_csv'` so Whoop's copy was stored but never surfaced — but it was a footgun waiting to fire. Fixed by renaming Whoop's to `spo2_whoop` and using `migration_007` to re-stamp history in place. The general rule: a `metric_type` literal means a specific kind of measurement, not "whatever the source called it". If two sources measure semantically different things, give them different `metric_type`s even when the underlying physical quantity overlaps. The `daily_metrics` view can still pick a single authoritative source per dashboard concept via WHERE filters — that's the right place to make the precedence call, not at ingest by overloading a type name.
78. **Wake-day attribution applies to the WHOLE recovery payload, not just the original four.** When a new recovery field shows up (Whoop adds something in a future API version, or we start writing one we ignored before), it carries `period_end = cycle end` like every other recovery row — same shape as the gotcha #74 bug. It MUST flow through `whoop_wake` on `period_start`, not `period_end::date`. The view comment on `whoop_daily` calls this out; the type-list inside the WHERE clause also tracks every recovery metric we wake-day attribute. Adding a new one is two places: the WHERE list + the `MAX(...) FILTER` projection. Don't be tempted to drop a quick `MAX(canonical_value) FILTER (WHERE metric_type = '…') GROUP BY (period_end AT TIME ZONE …)::date` because it's shorter — that's the bug.
79. **In-place re-stamps over delete+insert. Always.** `migration_007` re-stamps `metric_type` (and the embedded `source_record_id` substring) for every Whoop SpO2 row in place. Never deletes — Irfan's hard rule, and also the right move for an audit table: history stays continuous, no orphan rows, no risk that a partial failure leaves data in a degraded state. The `UPDATE … WHERE … = 'spo2_overnight_avg'` is naturally idempotent (after it runs, the WHERE matches nothing). Same pattern goes for any future column-renames / type-renames in this table.
80. **Skin temp has NO fixed clinical band by design.** No `st.skinTemp(v)` entry in `thresholds.ts`, no `LOW_FLOORS` entry. Unlike resting HR or SpO2 where there's a meaningful absolute population-level threshold, skin temperature varies enormously by ambient, by person, by season — the only useful signal is **deviation from THIS person's own recent normal**, which is what the drift engine already does (median + MAD, robust to outliers, recomputes as data accumulates). Adding a fake "fever = 38°C" band would either fire on warm-room nights or miss real febrile drift that starts at 36.5 instead of 37. Drift watches the move; the readout just shows the value + a cheap "vs your normal" delta.

### Cardiac BP — category + chart
81. **`bpCategory(sys, dia)` is the SINGLE SOURCE OF TRUTH for BP classification.** `thresholds.ts::st.bp` delegates to it; the Cardiac panel's category readout uses it; the TrendChart tooltip uses it. **Do not** add a second BP classifier anywhere — the KPI dot and the long-form panel readout cannot drift apart by construction, and that's load-bearing for trust (a KPI saying "good" while the panel says "Stage 2" would be an immediate credibility loss). If a future caller needs a different framing (e.g. a kid's BP ranges in a hypothetical multi-user app), add a NEW function rather than branching this one. Logic order matters: Low (provisional) → Crisis → Stage 2 → Stage 1 → Elevated → Normal; Elevated needs **both** sys 120–129 AND dia <80 per ACC/AHA (one common mis-implementation is to make Elevated an OR — that swallows Stage 1 dia cases).
82. **BP bands plot at actual mmHg y-values; the chart uses one shared y-axis, not separate territories.** I deliberately concat `BP_DIA_BANDS` + `BP_SYS_BANDS` and pass to the chart unchanged because the band ranges don't overlap (diastolic tops out at 119, systolic starts at 90 with most action above 120, and the divider at 95 makes the boundary visually unambiguous). The "territory" framing is a UX layer — `divider` + edge labels — not a coordinate-system layer. Don't be tempted to remap diastolic into the lower half of the chart and systolic into the upper half via custom y-scales: the lines would then NOT be at their actual mmHg values, breaking the at-a-glance read + the tooltip's honesty.
83. **Don't introduce per-metric y-axes on the same chart.** Same trap as the BP territory remap above. The current TrendChart is single-y-axis; if a future panel genuinely needs two metrics on different scales (e.g. SpO2 0–100 vs RHR 40–80), use `DualAxisChart` (Slice 7.2) — don't fork TrendChart into a half-and-half mode. The Cardiac BP chart sidesteps this by putting both metrics on the SAME natural unit (mmHg), which is the right move when units match.

### File-drop pipeline (Slice 4)
46. **Drive has no native move; `files.update` swaps `addParents`/`removeParents`.** `lib/google-drive.ts::moveFile()` is the only place that knows this — call it, don't try a delete+create elsewhere. Move failures are logged but don't downgrade the ingest verdict; the next run dedupes via `(source_slug, source_record_id)` upsert if the same file reappears in inbox.
47. **`GDRIVE_SA_KEY` is the service-account JSON BASE64-encoded**, not raw JSON. The setup runbook tells Irfan to `base64 -i key.json | pbcopy` before pasting into Vercel — newline mangling in env-var UIs is the documented hazard. The Drive client does `Buffer.from(...,'base64').toString('utf8') + JSON.parse`. Don't expect raw JSON; the auth will silently fail.
48. **Oxylink timestamp has NO SPACE before AM/PM** (`"10:38:13PM Jun 21, 2026"`), and the comma between day and year is INSIDE the quotes. The explicit `TS_RE` parser handles the AM/PM quirk; `csv-parse` (not a hand-rolled split) handles the quoted comma. Both invariants together — change either side without the other and you get silently mis-columned health readings.
49. **File-drop parsers' filter logic is the single source of truth for "valid row".** If a parser ever gets a refill path (full-history re-import), the same filter must be shared (gotcha #25 pattern). v1 has no refill route for Oxylink; keep the filter inside the parser but structure it so the rules live in one place.
50. **`processed/<source>/` and `failed/<source>/` are auto-created on first cron run**, but `inbox/<source>/` MUST be pre-created in Drive (its absence is interpreted as "source not configured" and the cron skips it silently). Adding a new parser requires both the registry entry AND the inbox subfolder.
51. **`parser.sourceFolder` is the Drive folder name; `parser.sourceSlug` is the DB key.** They CAN differ — Oxylink's slug is `oxylink_csv` (matches `sources.slug` in migration_001) but its Drive folder is just `oxylink` (cleaner UX in `inbox/`). `resolveRootStructure` takes `SourceFolderSpec[] = { slug, folderName }[]` — looks up by `folderName`, keys results by `slug`. The cron route builds the spec from `FILE_DROP_PARSERS[slug].sourceFolder`. **An early Slice-4 build looked up by slug and got `configured: false` on the live deploy despite the folder existing — silent failure, not an error**. If you add a new parser, the two fields' purposes are: `sourceSlug` = what goes into `health_observations.source_slug` (must match a row in `sources`); `sourceFolder` = what to type in Drive (whatever's friendliest). The mismatch is fine — the spec is the only place they're tied together.
52. **`?probe=1` on the file-drop cron route is the standard debug move when `configured:false` doesn't match what you see in Drive.** Short-circuits before any processing, dumps the service account's literal view of the root + inbox subfolders with `nameBytes` (each character's codepoint, so invisible characters like trailing spaces or zero-width joiners surface as anomalous integers). Catches: casing mismatch (Drive `name=` is case-sensitive exact-match), trailing spaces (the `Dexcom ` class of bug), wrong parent (folder under root instead of inbox), duplicate-`inbox` folders. Auth same as the cron (`CRON_SECRET` bearer). Don't add similar probes to other crons unless they hit the same opaque-folder-routing class of bug.
53. **Vercel's GitHub-App webhook can go stale repeatedly, not just once.** First seen in Slice 1 (gotcha #22), recurred in Slice 4. Symptom: `git push` succeeds but no new Vercel deployment appears within 60s. **Fast fix:** push an empty commit (`git commit --allow-empty -m "..." && git push`) — the new commit hash triggers a fresh webhook event. **Permanent fix:** Vercel → Project → Settings → Git → Disconnect → reconnect (also fixes it once for several months). Don't ignore — a stale push means the production deploy is testing against old code.
54. **Build maps from `DRIFT_METRICS`, not hand-written object literals.** `fetchMetricDrift` originally initialised its `grouped` map with a literal `{ rhr: [], hrv: [], ... }` listing all 8 metric keys. Adding SpO2 needed two more keys, and "the spec told me to add them" is the kind of footnote that goes unread on the 9th metric. Refactored to `Object.fromEntries(DRIFT_METRICS.map((m) => [m, []]))` so the next metric add is one-place. Same rule for any future map keyed by `DriftMetricId` — derive it from `DRIFT_METRICS`, don't enumerate. `LOW_FLOORS` stays `Partial<Record<DriftMetricId, LowFloor>>` so absence is expected; only metrics with a clinical floor get an entry.
55. **`spo2_avg` + `spo2_min` are concerning=down, acknowledgeGood=false** — same call class as RHR-down=neutral. SpO2 is bounded at 100 and Irfan already sits high, so upward drift near the ceiling isn't a physiological "win" the way HRV-up or weight-down is; the signal that matters is downward (nocturnal desaturation). Provisional pending Dr. Jose. Don't flip `acknowledgeGood` to `true` without that conversation.
