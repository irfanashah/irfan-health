## Stack

- Next.js 16.2.9 (App Router, Turbopack) + TypeScript
- Tailwind CSS v4 (CSS-based config via `@theme` in `app/globals.css` — **no `tailwind.config.ts`**)

## Decisions made

- **Dark mode default**, light toggle available, no system-preference following. Persists in localStorage per page load.
- **No `tailwind.config.ts`.** Tailwind v4 reads config from CSS (`app/globals.css`). Spec assumed v3; translated to v4 equivalents.
- **shadcn base preset = `base-nova` (neutral)**, not Zinc as the original spec asked. Visually near-identical; not worth hand-editing 30+ oklch variables.
- **Single-user auth.** Supabase email signup disabled. Only Irfan's account exists.
- **Vercel deploys from `main`.** Every push triggers production. No preview-branch strategy.
- **Vercel Pro plan** (upgraded mid-Slice-1). Required because Hobby caps cron at 2 invocations/day and our `0 */6 * * *` schedule runs 4×/day. Pro also gives function `maxDuration` up to 800 s — the refill/backfill/diagnose routes set `export const maxDuration = 800` to use the full ceiling.
- **OAuth tokens live in Supabase `oauth_tokens` table**, NOT Vercel env vars. Deliberate deviation from data-model spec §6 — documented at top of `slice-1-whoop-adapter-spec.md`. Service-role client reads/writes the table; tokens never reach the browser.
- **Whoop history starts at 2025-02-06** (first day Irfan wore Whoop). The cron-run `BACKFILL_START_DATE` in `adapters/whoop/index.ts` is set to `2026-04-15` (just before the 2026-04-28 STEMI) for routine catch-up runs. Full historical loads use `/api/refill/whoop` (ID-diff approach), which is faster and more reliable than the chunked sweep.
- **`adapters/whoop/api.ts` targets Whoop Developer API v2.** v1 endpoints return 404s — Whoop deprecated them.
- **Dashboard is intentionally minimal post-Slice-1.** Only `DiagnoseButton` is rendered (now showing both Whoop and Withings panels in one click). The Slice-1-era `RunNow`, `Refill`, and `Backfill` buttons + components remain in `components/` and their routes are live; just unrendered. Routine sync runs on cron; reconciliation is a manual job that re-imports the relevant button when needed.
- **Slice 2 default refill `targetStart` is `2025-01-01`**, same as Whoop. The Withings adapter `BACKFILL_START_DATE` matches. POSTing `/api/refill/withings` with `{ fromDate: '…' }` overrides per-call.
- **Withings `attrib` filter:** the adapter and refill both accept `0` (device-recorded), `1` (manual entry via app), `2` (manual override) only. They skip `4` (user objective), `5` (flagged wrong), `7` (creation stub), and any unrecognised value. The `ACCEPTED_ATTRIB` set lives in `adapters/withings/index.ts` and is mirrored inline (with a comment) in `app/api/diagnose/withings/route.ts` — change all three together if loosening.
- **Withings `buildBpRow` is the single source of truth for "what's a valid BP row"**, exported from `adapters/withings/index.ts` and imported by both the cron adapter (via the `withingsAdapter.fetchAndIngest` loop) and `/api/refill/withings`. Avoids drift (gotcha #25).
- **Slice 3 Note lives as an always-visible compact textarea, not a 5th tab.** The data model treats `note` as a peer `metric_type` value alongside `symptom`/`weight`/`glucose_fingerstick`, but standalone notes are rare enough that a tab slot would over-rank it. Always-visible "Quick note" keeps the path open without elevating it to one of the four core types.
- **Single polymorphic `updateEntry({kind,id,payload})` for Slice 3 edits, not per-type updaters.** Create paths stay per-type (`createWeight`, `createGlucose`, …) because their validation differs; updates centralise around the discriminated union so the `source_slug='manual'` guard lives in one place. Asymmetry between create + update is intentional.
- **Symptom severity is optional (nullable 1–5) in Slice 3.** Logging a symptom mid-event shouldn't force a number on you — the code + timestamp is the load-bearing signal; severity is incremental.
- **`source_slug='manual'` is the hard guard on Slice-3 edit/delete.** Every `updateEntry`/`deleteEntry` query chains `.eq('source_slug', 'manual')` with `{count: 'exact'}` — non-manual ids never match, so the action returns "not found or not editable" without distinguishing missing from forbidden. Application + query-level enforcement; no DB-side trigger.
- **Nightscout auth = static URL + read token, NOT OAuth.** No `oauth_tokens` row, no token refresh. `NIGHTSCOUT_URL` + `NIGHTSCOUT_TOKEN` live as Vercel env vars; the token is passed as `?token=…` on every request. The read-only role (subject `irfan-health`) is sufficient — we only ever GET.
- **Slice 5 `BACKFILL_START_DATE` = `2026-05-01`** (not `2025-01-01` as Whoop/Withings use). Nightscout history starts `2026-05-28` (Clarity backfill), and the G7 was the only CGM Irfan has ever worn — no older data can exist. Stretching the default back to Jan 2025 would mean ~17 empty 30-day refill chunks for zero gain. POST `/api/refill/nightscout` with `{ fromDate: '…' }` overrides per-call.
- **CGM plausibility band = 40–500 mg/dL** (not 10–600). Real CGM output starts at 40 — Dexcom G7's measurement range is 40–400 and Libre's is 40–500. Anything below 40 is a sentinel/special code (0, 1, "LOW" encodings), not a reading. 40–500 stays device-agnostic (covers both Dexcom and Libre) while excluding all sub-40 sentinels that a 10–600 floor would let through and pollute trends. If real readings ever get filtered, the skip count surfaces in `ingestion_log` and Diagnose; widen then.
- **Slice 5 `extras` omit-missing rather than null.** `buildCgmRow` writes `{ direction, device, noise }` excluding any undefined key. A backfilled Clarity row carries no `direction` key at all rather than `direction: null`. Querying `extras->>'direction'` returns null either way; this just keeps the JSON compact for the largest writer (Clarity backfill).
- **Slice 5 Diagnose default window = last 30 days** (not full history like Whoop). CGM volume makes a wide default expensive; the refill route is the right tool for true full reconciliation. Diagnose is the quick health check. `POST { fromDate, toDate }` overrides for the rare full check. Different from Whoop's panel deliberately — they're independent.
- **Slice 5 cron passes a strict 48 h window to the adapter** rather than relying on the adapter's last-success-end resolution. Catches missed runs without ever trying to backfill 3 weeks of history in a single 12-hourly tick. Refill is the only path that walks the full history.
- **`buildCgmRow` is the single source of truth for "what's a valid CGM row"**, exported from `adapters/nightscout/index.ts` and imported by both the adapter (cron + ingest) and `/api/refill/nightscout`. Same pattern as Withings `buildBpRow` — avoids drift (gotcha #25).
- **Slice 7.1 charts are custom SVG, NOT recharts.** The Slice-7 pre-spec notes mentioned recharts; the working prototype superseded that with hand-rolled SVG (`Sparkline`, `TrendChart`, `CGMChart`, `Donut`, `StackedBars`) tuned to the design language. Don't add a chart library — port `prototype-src/06-charts.jsx` whenever a new chart is needed.
- **Aggregation is server-side (`daily_metrics` view), not client-side.** CGM is ~288 rows/day; pulling raw and grouping in JS doesn't scale and obscures the time-window rules. The view does CGM stats + GST bucketing in SQL; the dashboard pulls one row per day for whichever range it needs.
- **Whoop daily-summary attribution = `period_end::date` in GST.** Recovery / strain / sleep / HRV / RHR for the cycle ending Tuesday morning lands on Tuesday's row (matches Whoop's UI). In-progress cycles have `period_end IS NULL` (gotcha #17), so the view naturally excludes the unscored current cycle. Don't switch to `period_start` — recovery would land on Monday instead.
- **Weight carry-forward is for the TREND CHART only, never the KPI.** The `daily_metrics` view returns weight = NULL on no-reading days (pure aggregation). `components/dashboard/utils.ts::carryForwardWeightForTrend` fills nulls only for the line chart. The "Latest weight" KPI reads from `fetchLatestKpis()` (actual most recent reading). Mixing the two would show a carried value as if it were today's reading.
- **Recovery-day counter date = 2026-04-28 (STEMI), not the prototype's April 5.** `prototype-src/02-data-layer.jsx` hard-codes April 5 as a placeholder; `CLAUDE.md` is canonical. `components/dashboard/thresholds.ts::STEMI_DATE` uses 2026-04-28 with explicit GST offset.
- **TIR is count-based, valid because sgv is ~5-min equispaced.** Both the `daily_metrics` view (per-day TIR in `cgm_stats`) and the Glucose panel (24-hour TIR donut) use count% as a proxy for time%. The view comments the assumption explicitly; if a future source ever writes non-uniform CGM cadence, switch both to a time-weighted calculation.
- **Glucose panel's 24h TIR is computed from the SAME 24h window the chart shows**, not from the view's per-day TIR. Otherwise the donut and the curve could appear to disagree at the rollover between days — UX confusion. The view's TIR is for the trend / Connections view (Slice 7.2).
- **Slice 7.2 honesty layer: every `r` is computed AFTER `pairedNonNull`** (drops days where either side is null), `n` is ALWAYS displayed next to `r`, and below `MIN_PAIRED_N = 10` the badge greys + the linear fit on the scatter is suppressed + the insight slot reads "Not enough paired days yet (n = X) — keep logging." Don't expose a "filter nulls = off" affordance; pretending zero is a value silently lies on this kind of data.
- **Insight + cascade prose is associational, never causal.** Audited against the prototype: "Short sleep nudged BP up" → "On shorter-sleep days, morning BP tends to run higher." Acceptable verbs: "ran higher / ran lower / linked with / tends to / averaged". Forbidden: "caused / led to / because of / drove". Same rule applies to any future on-dashboard prose.
- **Cardiac Readiness "today" uses a latest-complete fallback** rather than dashing through the day. If today's row lacks any of the five inputs (very common — today's cycle isn't scored yet until Whoop closes it overnight), the panel shows the most recent fully-scored day with an "As of <day> · today's cycle isn't scored yet" sub-note. Delta then compares the two most recent fully-scored days. Only "—" when no day in the window has all five inputs. Decided 2026-06-19 — friendlier UX than a persistent dash, still honest about what's actually being shown. The TREND chart stays strict (only fully-scored days).
- **Readiness never renormalises over missing inputs.** `computeReadiness` returns null if any of the five sub-scores can't be computed. Renormalising would silently change what "70" means day to day. The trend chart shows gaps; the headline uses the latest-complete fallback.
- **Annotated glucose markers reuse the already-pulled `fetchRecentManual(20)`** — no extra round-trip. Risk: on a heavy-logging day a within-window symptom could fall outside the last-20, in which case markers look incomplete. Trivial at current volumes; switch to a window-scoped uncapped query (`recorded_at ∈ [t0,tN]`) if it ever shows up as a real gap. Don't add a second query speculatively.

## Gotchas

### Build / project setup
1. **Hardcoded Tailwind colours kill dark mode silently.** `bg-gray-50` on a full-viewport wrapper covers the dark `body` even though `<html class="dark">` is being set correctly. Always use semantic tokens (`bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `border-border`, `border-input`, `ring-ring`, `bg-primary`, `text-primary-foreground`, `text-destructive`, `text-accent-teal/purple/amber`) on any new page.
2. **Next.js 16 deprecated `middleware.ts` → `proxy.ts`.** Warning only; still works. Rename in a future small slice.
3. **`create-next-app` refuses to scaffold into a directory containing arbitrary files.** Slice 0 worked around this by scaffolding in `/tmp` and copying in.
4. **`.gitignore` from `create-next-app` blocks `.env.local.example`** via the broad `.env*` rule. Added `!.env.local.example` exception.
5. **next-themes requires `suppressHydrationWarning` on `<html>`.**
6. **The `@AGENTS.md` import at the top of this file is load-bearing** — it pulls in the "this is Next.js 16, not your training data" notice. Keep it.

### Supabase
7. **`createClient` (server) is async** (`cookies()` is async in Next 16) — must be `await`ed. **`createServiceClient` (service) is sync.** Slice 1 spec mixed these up; fixed inline.
8. **Postgres `numeric` round-trips as either number or string** through PostgREST. The dedup pre-check in `upsertObservation` coerces both sides via `Number()` before `===` — without that, the "skipped" counter never increments even though dedup at DB level still works.
9. **Middleware must not redirect `/api/*` routes.** Spec's Slice 0 middleware redirected every non-`/login` route to login if unauthenticated; that swallowed Whoop's OAuth callback (the `code` param was lost on the redirect to `/login`). API routes self-enforce auth — session for `/api/ingest/whoop`, `CRON_SECRET` for `/api/cron/whoop`, public for OAuth callbacks.
10. **Supabase JS `.select()` silently caps at 1000 rows by default.** Bit us twice — first in the diagnose route (per-metric counts were truncated), then in the refill route's "fetch all existing IDs" step. Fix: either use `.select('*', { count: 'exact', head: true })` for count-only, or paginate with `.range(offset, offset + 999)` for actual rows.
11. **Batch upserts are all-or-nothing per statement.** One row with a check-constraint violation (e.g. null `period_end` from an in-progress Whoop cycle) fails the entire 200-row batch. Filter invalid rows before the batch call, don't rely on the DB to skip them.
12. **Frontend cursor state must be persisted in `localStorage`** for multi-click backfill UIs — React `useState` resets on page refresh, which silently restarts the cursor from "now" and re-walks the dense recent window. Cost us hours debugging the sweep before figuring this out.

### Source APIs — Whoop
13. **Whoop's developer API is v2 only** at `https://api.prod.whoop.com/developer/v2`. The v1 paths in the original spec returned 404.
14. **Sleep is at `/activity/sleep`, not `/sleep`.** Spec was wrong; cycle and recovery are at `/cycle` and `/recovery` (no `/activity/` prefix).
15. **Whoop requires the OAuth `state` parameter** on the authorization request, not just optional. We generate 32 random bytes hex, store in an httpOnly cookie (`sameSite: 'lax'`, 10 min TTL), and verify on callback. Without it Whoop returns `{"error":"invalid_state"}` immediately, before even rendering its approval page.
16. **OAuth handshake must happen on the live Vercel URL**, not localhost — Whoop's app registration only allows HTTPS redirect URIs. Local dev reads tokens from Supabase so this is fine post-handshake.
17. **In-progress cycles and sleeps have `null` start/end.** The current day's cycle (and sometimes the most recent sleep) won't have an `end` until Whoop finalises overnight. Inserting them violates the `chk_obs_time_coverage` constraint on `health_observations`. The refill route filters these out into `buildErrors`; the next cron run picks them up once Whoop scores them.
18. **Recoveries inside a fetch window can link to cycles just before it.** A recovery scored on 2025-01-01 morning links to a cycle that started on 2024-12-31 evening. If you only fetch cycles for `[fromDate, toDate]`, those recoveries silently drop because their `cycle_id` isn't in your `cycleMap`. Fix: widen the cycle fetch backwards by 14 days, but only emit `strain_score` rows for cycles whose `start >= fromDate` so you don't pollute pre-window data.
19. **Whoop rate-limits aggressively.** Stacking diagnose + refill + ingest in quick succession trips 429 on `/cycle`. Wait ~2 minutes and retry, or — better — verify in Supabase with a SQL `COUNT(*) GROUP BY metric_type` instead of re-hitting Whoop.

### Source APIs — Withings
- **Withings uses form-encoded POST for everything** — both the token endpoint (`/v2/oauth2`) and the measure endpoint (`/measure`) accept `application/x-www-form-urlencoded` POST bodies, including an `action` form field (`requesttoken`, `getmeas`). Don't send JSON.
- **Withings responses are wrapped**: `{ status: number, body: {...}, error?: string }`. `status === 0` means success; anything else is an API-level error even on HTTP 200. Always unwrap and check `status` before reading `body`. Surface `error` text on non-zero status.
- **Withings tokens rotate on every refresh.** New `refresh_token` returned in each `requesttoken` response. Persist the rotated pair to `oauth_tokens` immediately (handled in `refreshAccessToken`). Lose the new refresh token and you have to re-handshake from scratch.
- **Withings `getmeas` paginates via `{ more, offset }`.** Stop when `more !== 1`. Defensive: also stop if `more === 1` but `offset` didn't advance — prevents infinite loop on a misbehaving response.
- **Withings unit field is a base-10 exponent**, not a unit string. Real value = `value × 10^unit`. Example: `{ value: 1200, unit: -1 }` → 120 mmHg. Don't forget to `Math.round()` before storing in `smallint` columns.
- **Withings `attrib` codes encode measurement provenance**, not just metadata. `0` = device, `1` = manual app, `2` = manual override are real; `4` = objective (a target, NOT an actual reading), `5` = flagged wrong, `7` = creation stub. Filter against an explicit allow-list, don't reject only the obvious bad codes.
- **Measurement groups can contain non-BP measurements.** A pulse reading without systolic+diastolic isn't a BP reading and must not land in `bp_readings`. Filter on presence of both `type === 9` and `type === 10` before building a row.

### Vercel
20. **Vercel function timeouts:** Hobby caps at 60 s regardless of `maxDuration`. Pro defaults to ~180 s; `maxDuration = 800` is the Pro ceiling. When the function exceeds its budget, Vercel returns a plain-text "An error occurred…" page — the frontend's `JSON.parse` chokes on it with `"Unexpected token 'A'…"`. That error means "function timed out", not "adapter bug".
21. **Vercel cron limits:** Hobby allows 2 invocations/day total. `0 */6 * * *` = 4/day blocks the entire deploy (not just disables the cron). Required Pro upgrade.
22. **GitHub-App webhook can go stale after a Vercel plan upgrade.** Pushes silently stop triggering deploys despite the Git settings page still showing "Connected". Fix: Settings → Git → Disconnect → reconnect. Confirmed in Slice 1.

### Operational
23. **Session-authenticated routes can't be hit by `curl` from the terminal.** `/api/ingest/*` and `/api/refill/*` check `supabaseUser.auth.getUser()` against the Supabase session cookie. Without the cookie, you get `{"error":"Unauthorised"}` and 401 — even when logged into the dashboard in another tab, because the cookie lives in the browser, not the shell. Quickest one-off: while logged in, paste a `fetch('/api/refill/...', {...})` snippet into the browser dev console — runs in your authenticated tab, cookie tags along automatically. Alternatively re-import a button into `app/page.tsx` and click it.

### Loading patterns
24. **Prefer ID-diff refill over chunked sweep for any "full historical load" task.** The chunked sweep approach (walk windows in N-day chunks, dedup per row via SELECT-then-upsert) is slow (~50 ms × N rows per chunk for the dedup SELECT) and error-prone (cursor management, partial timeouts, every chunk creates an `ingestion_log` row). The ID-diff pattern — fetch the full list of IDs from the source, pull existing IDs from the DB (paginated), diff in memory, batch-upsert only the missing ones — completed the entire 17-month Whoop history in ~13 s after we landed on it. Use the sweep only when memory diff is impractical (millions of records) or when the source doesn't expose stable IDs.
25. **When you fix a row-validity filter in the refill route, back-port it to the main adapter too.** The refill route (`/api/refill/whoop`) was hardened with null-`period_start`/`period_end` filters for in-progress cycles/sleeps. The main adapter (`adapters/whoop/index.ts`) — which the cron uses — was missed initially. Every cron run silently landed as `status = 'partial'` for ~5 errors against the in-progress cycle until we noticed and ported the same filter across. The two paths share the same `health_observations` constraints; whatever the refill skips, the adapter must skip. Same rule will apply per-source going forward: `adapters/<source>/index.ts` (incremental cron) and `/api/refill/<source>/route.ts` (full-history reconciliation) must agree on what gets filtered.

### UI / forms (Slice 3)
26. **`adapters/_lib/ingestion-log.ts:createIngestionLog` mandates a fetch window**, but manual writes have no window — schema already allows nulls (`fetch_window_start/end` are nullable, "null for episodic imports" per data-model spec §1). Slice 3's `actions.ts` inserts the `ingestion_log` row inline with `status='success'` + `records_*=1` + `raw_payload`=form values and no window. Don't try to reuse `createIngestionLog` for manual paths; either keep them separate or relax the helper to accept optional windows.
27. **Use `{ count: 'exact' }` on Supabase `.update()` / `.delete()` to detect "guard failed → no rows touched".** Slice 3's `updateEntry`/`deleteEntry` chain `.eq('source_slug', 'manual')` and inspect the returned `count` — zero means either the id doesn't exist or it's not a manual row, and the action returns the same "not found or not editable" message in both cases (deliberately — don't leak whether a non-manual id exists). This is the right pattern for any future row-level write guard.

### Nightscout / CGM (Slice 5)
28. **Cross-slice import: `adapters/nightscout/index.ts` imports `mgdlToMmol` from `@/app/log/_lib/glucose`.** That helper was written for Slice 3's manual-entry path; Slice 5 reuses it directly rather than duplicating the divisor + rounding. The path `adapters/ → app/log/_lib/` is unusual but intentional. Any future glucose-source adapter (Tidepool, labs with fasting-glucose markers) should reuse this same helper rather than copying the conversion. If it ever needs to move, `adapters/_lib/glucose.ts` is the natural home — but don't move it without updating both Slice 3 and Slice 5 imports.
29. **Nightscout `/api/v1/entries.json` returns 10 entries by default.** You MUST pass `count=…` (we use `100000`) on every request, or you'll silently truncate windows. The cron is small enough that the cap doesn't matter, but the refill's 30-day chunks would lose almost everything without it. Same risk applies to any other Nightscout endpoint (treatments, profiles).
30. **`extras` keys for Nightscout are written omit-missing**, not `null`. Backfilled Clarity rows have no `direction`; the row's `extras` simply has no `direction` key, vs. `{direction: null}`. `extras->>'direction'` returns null either way in SQL, so this is purely about JSON compactness for the bulk-import case. If you later need to distinguish "no direction reported" from "explicitly null", revisit this.

### Dashboard (Slice 7.1)
31. **All GST bucketing in `daily_metrics` goes through `AT TIME ZONE 'Asia/Dubai'`** — never mix UTC and local time in the same predicate. The view uses three flavours: `(ts AT TIME ZONE 'Asia/Dubai')::date` for day-buckets, `(ts AT TIME ZONE 'Asia/Dubai')::time BETWEEN TIME '05:00' AND TIME '11:00'` for time-of-day windows (morning BP, fasting glucose), and the same construct as a CASE sort key in `DISTINCT ON` to prefer morning readings. Any future per-source rule that involves "Irfan's local day" must use the same pattern. Asia/Dubai is fixed UTC+4 — no DST surprises.
32. **The prototype's CSS theme was `[data-theme="dark"]`; Slice 7.1's port uses `.dark`/`.light` to match next-themes' `attribute="class"`.** Don't introduce a parallel `data-theme` attribute — the dashboard CSS picks up the same class next-themes already toggles on `<html>`. If you ever wire a second theme mechanism, the dark/light vars will desync on toggle and one of the two will silently win.
33. **Dashboard body styles are scoped to `.app`, not the global body.** The prototype's CSS had `body { background: var(--bg); }` which would override Tailwind's `bg-background` on `/log` and `/login`. The port moves background + font onto `.app` so the rest of the app's semantic tokens still rule. New dashboard-only styles should hang off classes inside `.app`, not the root.
34. **Charts treat `null` accessor results as gaps, not zeros.** `TrendChart` segments the path on null and only draws within contiguous runs of valid values. Don't replace nulls with 0 in the view or the data module — that would draw a fake "weight = 0 kg" line on no-reading days. Empty-array data renders an "empty note" instead. The same rule applies if you add a new series.
35. **`router.refresh()` after a write is the Slice-7 mutation pattern, not optimistic prepend.** Quick-log calls a Slice 3 server action then `router.refresh()` — Next.js re-runs the dashboard's server component, the recent feed + KPIs come back fresh, no client-side stale state to manage. Use the same pattern for any future dashboard write.

### Connections (Slice 7.2)
36. **Pair before you compute.** Every `r` (Correlation Explorer + Activity pacing) goes through `pairedNonNull(xs, ys)` first; raw arrays are never fed into `pearson`. If you add a new correlation panel, route it through the same helper or you'll silently compute over zeros-where-nulls-should-be. `MIN_PAIRED_N = 10` is the canonical threshold; import the constant rather than redefining it.
37. **Readiness is null-or-full, never partial.** `computeReadiness` returns null on any missing input. The trend chart skips null days; the headline uses `resolveTodaySnapshot` which walks back to the latest fully-scored day. If you ever need a partial score, add a new function — don't soften `computeReadiness`, or every downstream consumer's "score" silently means something different.
38. **The associational-prose discipline applies to every word the dashboard renders, not just the explorer.** Sleep cascade, pacing advice, headline notes — all audited. New copy goes through the same filter: descriptive verbs only ("ran higher", "tends to", "linked with"), never causal ("caused", "led to", "because of"). One leaked "caused" undoes the rest.
39. **Markers reuse the existing `fetchRecentManual(20)` payload.** No second server fetch for the Annotated Glucose panel — it filters the already-pulled recent entries to those whose `recorded_at` falls inside `[t0, tN]` of the CGM 24 h window. Caveat: a heavy-logging day could push an in-window symptom outside the last-20. If markers ever look incomplete, switch to a window-scoped uncapped query; don't add a second query speculatively.
